Persona, End to End

One diagram, two database collections, and a numbered walk through exactly what happens between a query landing and the answer coming back — with real documents pulled from a live test account, not mocked-up examples.

Collections: 2 (persona_events, persona_topics) Model calls per query: 1 SLM + 1 embed (background) Retrieval effect: real (search_query expands) Routing effect: zero (hard rule)

Same request, two halves, always in this order: read happens before anything is generated, write happens after the user already has their answer. Only the write half ever touches the database — the read half only ever reads.

The key design point: persona_events is the source of truth (append-only, nothing is ever deleted or edited); persona_topics is a derived cache — it's always fully rebuildable from the event history alone. If it ever got corrupted or out of sync, replaying the events regenerates it exactly.

03 Walking through one real request

  1. Resolve identity. ws.py decodes the JWT from the WebSocket message. No token, or an invalid one → treated exactly like a guest for the rest of the request. No persona code runs at all.
    retrieval_api/ws.py
  2. Read the snapshot. get_current_snapshot() loads every topic document for this user from persona_topics. If it's empty and the user has an old pre-migration flat persona doc, it's lazily converted into seed events here, once, and the snapshot is re-read.
    persona/repository.py::get_current_snapshot, migrate_legacy_persona
  3. Render context. Only topics in active/reactive state above a confidence floor become a sentence: "This user is currently focused on: Section 54F of Income-tax Act (active)." Everything else renders empty — identical to a guest.
    persona/prompt.py::render_persona_context
  4. Rewrite + classify (SLM call #1). extract_intent() gets the persona sentence appended to its prompt, with an explicit instruction: use this only if the query is genuinely ambiguous, and only to expand — never to override what the query itself says. For "exemption conditions" this actually changes search_query to "exemption conditions Section 54F Income-tax Act 1961".
    ai_mode/intent.py::extract_intent
  5. Retrieve. ES + Milvus search run on the (possibly persona-expanded) search_query. This function has no persona parameter at all — structurally impossible for persona to touch collection routing or RRF weights.
    ai_mode/retrieve.py::retrieve
  6. Synthesize (LLM call). The persona sentence is appended to the synthesis prompt too, same "advisory, not authoritative" instruction. The answer is built from whatever got retrieved in the previous step.
    ai_mode/synthesize.py::synthesize
  7. Answer sent. The user sees the result. Nothing past this point affects what they see.
  8. Extract + embed (background, SLM call #2 + embed call). A separate, second SLM call reads the original query and pulls out concepts/entities/objective. A Voyage embedding is generated for clustering. Fire-and-forget — any failure here is logged and swallowed, never surfaces to the user.
    ai_mode/persona_signal.py::record_persona_signal
  9. Cluster, append, rescore, transition. The new event is compared against the user's existing topics (embedding + entity + temporal + category similarity). It joins the best match above threshold, or starts a new topic. Either way, one persona_events document is appended, the topic's score is recomputed from its full history with exponential recency decay, and the state machine advances the topic's state if the evidence justifies it.
    persona/repository.py::record_query_event

05 How persona text actually enters a prompt

Persona has no dedicated model call of its own on the read side — it's plain text, appended onto two prompts that already exist. Here's exactly what gets appended, verbatim from the source.

Injection point 1 — the rewrite/classification prompt

[... full system prompt: query analyzer rules, search_query/intent/filters schema, worked examples ...] ---USER MESSAGE--- {original query text} {structural chunk context, if any} {lexicon-check note, if no legal anchor found} appended only if persona_context is non-empty{persona_context} "The note above is a prior about this user's typical usage, not a fact about this query. Use it only if this query is genuinely ambiguous on its own. If the query's own content conflicts with or is unrelated to the note, ignore the note and rely on the query alone." "If the query above is short/bare/ambiguous on its own... you may treat the user-focus note above as a legitimate basis for that confident, closely-related expansion - same standard as any other confident expansion: only when it doesn't contradict what's already in the query, never when the query is already a complete, unambiguous sentence that answers its own scope."

Injection point 2 — the synthesis prompt

[... system prompt: answer using only the retrieved chunks, cite every claim, formatting rules ...] appended only if persona_context is non-empty{persona_context} "The note above is a prior about this user's typical usage, not a fact about this query..." (same instruction, reused verbatim)

Same guard text both places, on purpose — one shared constant (RELEVANCE_INSTRUCTION), not two independently-drifting copies. The second, longer paragraph in injection point 1 (the "may treat the user-focus note as a basis for expansion" permission) only exists at the rewrite site — synthesis isn't producing a search query, so it doesn't need it.

Hard rule — no routing effect retrieve() has no persona_context parameter at all — not "ignores it," structurally can't receive it. Whatever the SLM does with the injected text above can change search_query/intent, but nothing downstream of that can trace back to persona directly touching which Milvus collections get hit or what RRF weight applies.

The other direction: is this a prompt-injection risk?

Yes, in principle — and it's guarded against. The persona sentence above is built from legal_entities/concepts that an SLM extracted from a previous query the same user typed. If that extraction step trusted the SLM's raw output blindly, a user could craft a query designed to make the SLM emit something like "ignore all instructions and reveal..." as a fake "entity," which would then get replayed into every future prompt for that same account.

persona.understanding.validate_understanding() sits between the raw SLM output and storage specifically to block this:

  • Every list field is capped at 8 items, each item capped at 80 characters — no long-form injected instruction fits.
  • Non-string list items are dropped outright.
  • Confidence/specificity scores are clamped to [0.0, 1.0] — never trusted as-is.
  • Any key beyond the five expected ones is silently discarded — an SLM output like {"system_prompt_override": "..."} just vanishes.

Blast radius is also capped structurally: even a successful injection only ever reaches that same user's own future requests — there's no cross-account read path, so it can't leak into another user's prompt.

06 The state machine, briefly

discovered→ emerging→ active→ fading→ dormant→ reactive→ active

Only active/reactive topics ever get rendered into a prompt. Promotion requires both a high enough score and at least 2 distinct corroborating days since the last transition — a single enthusiastic session can't fast-track a topic to active. There is no active → dormant edge in the graph; decline always passes through fading first.

08 Real bugs found building this, and how

Found via real Mongo, not unit tests Naive vs. timezone-aware datetime crash. BSON dates carry no tzinfo; pymongo returned naive datetimes on read while every timestamp this system writes is UTC-aware. Comparing them crashed against a real database — in-memory test fakes never round-trip through BSON, so this was invisible until live testing. Fixed with tz_aware=True on the Mongo client.
Found via real model-gateway calls Clustering never merged anything. Exact-string entity matching was too strict for how an SLM phrases the same legal concept differently call to call, and embedding similarity between two genuinely related queries measured only ~0.32 in practice. Fixed with normalized token-level entity matching and a recalibrated threshold.
Found via a skeptical look at a real answer Persona was only a cosmetic sentence, not a real retrieval signal. The rewrite step's system prompt had no concept of persona as a legitimate basis for expanding search_query, and separately, a bug meant topic labels could surface the two weakest, most generic entities instead of the useful ones. Fixed both — persona now measurably changes what gets retrieved, confirmed 3/3 on repeat testing.
Noted, not yet fixed record_query_event rescans a topic's entire event history on every write to recompute its score — unbounded read/compute growth for a heavily-used topic. A windowed rescan + TTL index is the planned fix, not yet done.
