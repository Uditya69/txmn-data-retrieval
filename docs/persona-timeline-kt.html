The Persona Timeline

Every logged-in user's query becomes one evidence-weighted event. Events cluster into topics, topics accumulate a recency-decayed interest score, and a topic only gets called "active" once several separate sessions corroborate it — so a two-day rabbit hole never gets mistaken for a real shift in what someone actually researches.

Storage: append-only events + derived cache Scoring: exponential decay, not lifetime average States: 6 (discovered→…→dormant) Model calls per query: 1 SLM + 1 embed Routing/RRF effect: zero
Status: implemented on feat/persona-interest-timeline, not yet merged to dev. It replaces the earlier flat, single-document persona (merged in PR #5) end to end — nothing runs both models at once.

01 What it's for

Instant and AI Mode are stateless by default — every query is answered with no memory of who's asking. Persona is the opt-in exception: for a logged-in user only, it builds a lightweight, evolving picture of what they research, and feeds a short, hedged sentence about it into the AI Mode synthesis (and query-rewrite) prompts. A guest gets byte-identical behavior to a world where persona doesn't exist — no lookup, no write, no latency.

The thing this replaces (merged in PR #5, still on dev until this branch lands) kept one Mongo document per user: a lifetime average across six fixed category tags, plus a majority-vote expertise level. It worked, but it couldn't answer the question that actually matters for personalization: what is this user working on right now, as opposed to what they've ever asked about. A user who did six months of IBC research and pivoted to GST last month still read as "IBC-leaning" for a long time under a lifetime average.

This system answers that instead, by treating persona as a timeline, not a snapshot: every query is an event, events build up topics, and topics carry a state (is this newly discovered, sustained, fading, or dead) that only moves when the evidence for it is real.

02 The unit of evidence: one query, one event

After every successful AI Mode response for a logged-in user, one background (fire-and-forget, never blocking the reply) call turns that query into a Query Understanding Record — a single cheap SLM call, same role="slm" the rest of AI Mode already uses:

{
  "concepts": ["director liability", "corporate debt"],
  "legal_entities": ["IBC"],
  "research_objective": ["determine liability"],
  "specificity": 0.84,
  "confidence": 0.92
}

That raw model output is never trusted as-is. persona.understanding.validate_understanding() strips anything outside the expected shape — wrong types, extra keys, oversized strings — before it's stored. This isn't paranoia for its own sake: the concepts/entities eventually get interpolated verbatim into a future synthesis prompt for that same account, so an unvalidated field is a same-account prompt-injection seam. A malformed or empty model response means no event is recorded at all for that query — same fail-closed instinct the old expertise-signal extractor used, just applied to a richer payload.

Alongside the understanding, one evidence_weight number captures how much this specific query is worth as a signal, from persona.evidence:

SignalWeight
Query submitted+1 (always present, floor)
Result clicked+2
Document opened+3
Document read deeply+4
Repeated related query+5
Document saved+6
Returned to topic later+8

Only "submitted" is wired up today — the frontend doesn't yet report clicks/opens/saves, so every event currently carries the floor weight. The other six signals exist because a search with no follow-up and a search that ends in a saved document shouldn't count the same, the moment that instrumentation lands upstream. Nothing downstream needs to change when it does.

03 Queries become topics, not categories

The old system's unit of affinity was one of six fixed tags (acts/rules/caselaws/…). This system's unit is a topic: an open-ended cluster the data itself creates, identified by nothing more than "queries that look and feel related." Every new event is scored against the user's existing topics on four signals, persona.clustering.combined_similarity():

weighted 0.5 / 0.25 / 0.15 / 0.10
SignalWhat it measures
Embedding cosine similaritySame Voyage query_embed call the rest of the repo uses (hard rule 1) — reused here purely as a vector for in-app comparison, never compared against the Milvus corpus
Legal-entity overlapJaccard over the extracted entities/concepts
Temporal proximityExponential falloff, ~0 by 48h apart — two queries five minutes apart look related; two queries three months apart don't, on this signal alone
Category overlapJaccard over AI Mode's own intent tags — free signal, no extra model call

Score ≥ persona_cluster_similarity_threshold (default 0.6) joins the closest existing topic; below it, a brand-new topic starts in the discovered state. There's no "closest, even if weak" fallback — an unrelated query never gets force-attached to whatever topic happens to be nearby.

Within one topic, a gap since the last event beyond persona_episode_gap_hours (default 7 days) opens a new research episode under the same topic, rather than pretending it's continuous activity. A user who did "GST input tax credit" in January and comes back to "GST registration cancellation" in March gets one topic, two episodes — the topic-level identity persists, but the system doesn't claim they were thinking about GST every day in between.

Explainability Every stored event keeps its own winning clustering_score and the signal breakdown that produced it (persona.repository.explain_assignment()) — "why did this land in this topic" is always answerable from the event itself, no recomputation needed.

04 Topics get a score, and the score forgets on purpose

The old category_affinity was a cumulative mean — after 500 queries, a genuine change in focus took hundreds more to move the number. persona.scoring.interest_score() replaces that with an exponentially decayed sum:

score = 1 - exp(-raw / 50),  where raw = ∑ evidence_weightᵢ · exp(-λ · age_in_daysᵢ)

Two deliberate properties fall out of that one formula:

  • Old evidence fades smoothly. λ (persona_decay_lambda, default 0.03/day) controls how fast — no hard cliff at some fixed window, just a continuous discount. A topic quiet for three months scores lower than it did at its peak, without needing a "days since last event" special case anywhere.
  • One event can't spike a topic to certainty. The 1 - exp(-raw/50) wrapper saturates — even the single highest-weight possible event (all seven signals firing at once, raw weight 29) lands well under 1.0. Reaching a high score takes repeated, decay-surviving evidence, not one enthusiastic session.

The whole function is pure: same event list, same "as of" timestamp, same λ → same number, every time. No model call anywhere in the scoring path — the SLM call already happened at extraction time, and everything from here down is arithmetic.

05 The state machine: hysteresis against rabbit holes

A raw score crossing a threshold isn't enough to call a topic "active" — that would let one unusually engaged afternoon look identical to a sustained research focus. Every upward move also requires persona_min_sessions_per_transition (default 2) distinct calendar days of corroborating evidence since the topic's last transition. Downward moves only need the score to actually decline.

discovered→ emerging→ active→ fading→ dormant→ reactive→ active

Two edges are load-bearing, not incidental:

  • No active → dormant edge exists in the graph. A declining topic always passes through fading first — the state-transition function (persona.state_machine.next_state()) simply has no code path that skips it, so this is guaranteed by construction, not by a runtime check.
  • dormant → reactive, never straight back to discovered. A user who comes back to a dead topic six months later keeps its original discovery date and every past episode — the topic document is reused, not recreated. reactive then needs the same corroboration as any other promotion before it's trusted as active again.

Pivot detection (persona.state_machine.detect_pivot()) is just a read over two topics' states: one in fading/dormant, another independently in active/reactive. Because reaching active/reactive already required the corroboration above, a pivot can never be reported off a single day's score crossover — the guarantee is inherited, not re-implemented.

06 Reading it back: what actually reaches the model

persona.prompt.render_persona_context() looks only at topics currently in active/reactive state above persona_context_confidence_floor (default 0.15) — a topic that's fading or below the floor is invisible here, regardless of how dominant it was historically. A brand-new user, or one with nothing above the floor, gets an empty string: identical to a guest.

"This user is currently focused on: GST (active); IBC (reactive)."

That sentence is always followed by the same hedge (RELEVANCE_INSTRUCTION, unchanged verbatim from the earlier system): this is a prior about typical usage, not a fact about this query — ignore it if the query's own content conflicts. Persona is never allowed to overrule what the query actually says.

For a genuinely ambiguous current query, render_topic_hypotheses() can additionally surface weighted candidate readings — but only when two or more of the user's topics clear the confidence floor for that specific query's embedding. One clear candidate renders nothing extra; forcing a false choice would be worse than silence.

"Possible topic interpretations for this query, by confidence: IBC 0.81; GST 0.19."
Hard rule — don't touch Persona context (including hypothesis weighting) only ever reaches extract_intent's and synthesize's prompt text. retrieve() — the function that decides which Milvus collections get searched and at what RRF weight — has no persona_context parameter at all. There's no code path for persona to become a routing or fusion signal, structurally, not by convention. See CLAUDE.md rule 4 and test_run_ai_mode_persona_context_never_reaches_retrieve_or_alters_routing.

fire-and-forget asyncio.create_task"]

+ gateway.embed(query_embed)"]
  M --> N["record_query_event()
cluster -> append event -> rescore -> transition"]

Where each hop lives:

  1. retrieval_api/ws.py — resolves user_id from the WS message's access_token, reads the persona snapshot (with a lazy legacy-doc migration on first touch), renders context, and after a successful AI Mode reply schedules the write as a tracked background task.
  2. retrieval_api/ai_mode/persona_signal.py — extract_query_understanding() (the one SLM call) and record_persona_signal(), which wraps the whole write in a broad except Exception so a down Mongo or gateway can never surface into the websocket handler.
  3. persona/repository.py::record_query_event() — the actual pipeline: validate → cluster → append to persona_events → rescore the topic from its full event history → run the state machine → upsert persona_topics.
  4. persona/repository.py::get_current_snapshot() / persona/prompt.py — the read side, called at the top of the next request.

Both the read and write sides degrade the same way on failure: an unreachable Mongo means empty persona context for that request, or a silently dropped write — never a crashed /ws/search call.

08 Legacy users, tuning, and what's still open

A user with a pre-existing flat personas document (from PR #5) isn't bulk-migrated. The first time their snapshot comes up empty, migrate_legacy_persona() reads that old document (never writes to it, never deletes it) and seeds one low-weight event per non-zero category it had — a synthetic starting point that decays away naturally under the new scoring instead of being thrown out or crashing the request.

Every threshold mentioned above is a PersonaSettings field with a default, overridable via env var without a code change:

SettingDefaultControls
PERSONA_DECAY_LAMBDA0.03How fast old evidence stops counting
PERSONA_CLUSTER_SIMILARITY_THRESHOLD0.6How closely a query must match to join an existing topic
PERSONA_EPISODE_GAP_HOURS168 (7d)Gap that starts a new episode within a topic
PERSONA_MIN_SESSIONS_PER_TRANSITION2Corroborating days required to promote a topic's state
PERSONA_CONTEXT_CONFIDENCE_FLOOR0.15Minimum score to appear in rendered context at all

Nothing new to provision in Mongo or Milvus: persona_events/persona_topics are schemaless collections created on first write, their indexes are created idempotently at app startup (main.py's lifespan, same pattern as auth's refresh-token indexes), and topic-similarity vectors are plain arrays compared in-process — no Atlas $vectorSearch index, no new Milvus collection, no new model-gateway role.

10 Gotchas & FAQ

Does this affect what gets retrieved?
Never. Persona only ever shapes prompt text for the LLM/SLM calls — see §06's hard rule. Milvus collection routing and RRF weights are identical with or without it.
Why not just re-ask an LLM "what's this user's persona?"
Expensive per query, non-deterministic, hard to test. Everything past the one extraction call — clustering, scoring, state transitions — is plain, reproducible arithmetic on purpose.
What if the frontend never adds click/open/save tracking?
Nothing breaks — every event still carries the "submitted" floor weight and the system works, just with a coarser evidence signal than it's designed to eventually use.
Can a topic's score hit exactly 1.0?
No, by construction — the saturating transform in §04 only approaches 1.0 asymptotically.
Is the old personas collection deleted?
No, and there's no plan to bulk-migrate or drop it. It's read once per user, lazily, on their first post-cutover request, and left alone after.
