The Instant Classifier

A small, fast model that reads a search query and decides which search engines should even bother looking. No LLM, no embeddings — just old-fashioned text features and logistic regression, retrained by hand when it gets something wrong.

01 What it's for

Instant Mode can search two very different backends: Elasticsearch (lexical/keyword matching — great for "Section 52", exact citations) and Milvus (vector similarity — great for "how do people avoid paying tax on rental income", i.e. meaning, not exact words). Querying both every time and merging results costs latency and can actually make results worse when one backend just isn't relevant to a given query.

The classifier's whole job is to look at the raw query text and pick one of three labels before anything is searched:

KEYWORD → Elasticsearch only INTENT → Milvus only HYBRID → both, RRF-fused

It replaced an older hand-written heuristic (query_tokenizer.classify_query_shape()) that used regex rules to guess query shape. This is a trained model instead — same idea, better calibrated, and it reports a confidence score the old heuristic couldn't.

02 What it looks at

There are no embeddings and no LLM call here on purpose — the design goal was sub-5ms, CPU-only. The model is a scikit-learn Pipeline of a FeatureUnion feeding a LogisticRegression. Six feature groups look at the query text in parallel:

packages/common/src/common/instant_classifier/features.py

Mental model Think of it as "does this query smell like a citation lookup, or does it smell like a plain-English question?" — every feature above is one sniff test, and logistic regression just learns how to weigh the sniffs.

03 Is this "AI"? What kind of model is it, really?

No transformer, no GPT-style anything, no neural network at all. It's 1990s-era machine learning: TfidfVectorizer + LogisticRegression from scikit-learn. If "AI" in your head means ChatGPT-style generative models, recalibrate — this is closer to a spam filter than to a chatbot. That's not a compromise; it's the point (see the sub-5ms latency budget in §02).

What "the model" literally is on disk

instant_classifier_model.joblib is a pickled Python object — specifically an sklearn.pipeline.Pipeline containing two fitted objects, saved via joblib.dump() (pipeline.py:25). Nothing more mysterious than that:

  1. The fitted FeatureUnion — this is mostly two fitted TfidfVectorizers, each holding a vocabulary: a dictionary mapping every word/n-gram seen during training to a column index, plus the IDF weight for each. The four hand-written featurizers (regex/gazetteer/structural/intent-language) don't need fitting — they're deterministic functions of the text, always fitted-as-a-no-op.
  2. The fitted LogisticRegression — literally one number (a weight) per feature column, per class, plus one bias number per class. For 3 classes and, say, ~2,000 TF-IDF columns, that's roughly 6,000 floating-point numbers total. That's the entire "brain." joblib.load() just deserializes those numbers back into memory.

What happens, mechanically, on one query

Take "can I claim HRA if I live with my parents" as a concrete walk-through:

  1. Text → numbers. Every featurizer in §02 turns the string into a fixed-length vector of numbers — a mix of 0/1 flags (regex hits, question words, modals) and TF-IDF weights (how rare/distinctive each word or char-chunk is, relative to the training set). All six groups get concatenated into one long row vector, say 2,015 numbers.
  2. Numbers → 3 raw scores. Logistic regression does one matrix multiply: scores = weights · features + bias — a weighted sum, once per class (KEYWORD, INTENT, HYBRID). This is the entire "inference" step, computationally: no attention, no layers, no iteration — one dot product per class.
  3. Scores → probabilities. A softmax turns the 3 raw scores into 3 probabilities that sum to 1, e.g. {KEYWORD: 0.04, INTENT: 0.91, HYBRID: 0.05}.
  4. Probabilities → label. argmax picks INTENT at 0.91 confidence — comfortably above the 0.8 threshold, so it's used as-is.

Every step above is standard linear algebra you could do by hand on paper for a small enough vocabulary. There is no hidden reasoning, no context window, no "thinking" — it is a fixed function of the input text, output in fractions of a millisecond.

The dataset — what it actually looks like

Not embeddings, not scraped text — a hand-curated, hand-labeled JSONL file, one JSON object per line:

{"query_text": "Section 52", "label": "KEYWORD", "source": "manual", "date_added": "2026-08-20"}
{"query_text": "u/s 54F", "label": "KEYWORD", "source": "manual", "date_added": "2026-08-20"}
{"query_text": "CIT vs Infosys Ltd", "label": "KEYWORD", "source": "manual", "date_added": "2026-08-20"}
{"query_text": "how do I evade tax legally", "label": "INTENT", "source": "manual", "date_added": "2026-08-20"}

train.jsonl has exactly 60 rows; eval_frozen.jsonl has exactly 24 rows, split off and frozen so every retrain is scored against the same fixed yardstick. That's it — there's no scraped corpus, no synthetic augmentation, no crowd-sourced labeling. Every row was written by a person who decided what label a realistic query should get. 60 examples is tiny by deep-learning standards, but it's enough for logistic regression over a handful of engineered features — the model isn't trying to learn "language," it's trying to learn "which of these ~15 signals correlates with which label," and 60 labeled examples is plenty of signal for that.

Why not use a real LLM/transformer for this?

AI Mode elsewhere in this repo does use an SLM (small language model) for query rewriting and an LLM for synthesis — those are genuinely open-ended generation tasks that need that machinery. This classifier's job is a closed, 3-way multiple-choice question asked on every single keystroke of Instant Mode, so it gets the cheapest tool that's accurate enough for the job.

04 How it decides

def classify(query):
    proba = pipeline.predict_proba([query])[0]
    label = pipeline.classes_[proba.argmax()]
    confidence = float(proba.max())
    return label, confidence

def resolve_routing(label, confidence, threshold):
    if confidence < threshold:
        return HYBRID   # when unsure, search everything
    return label

Two things worth internalizing:

  • Empty query → instant HYBRID, 0.0 confidence — never even touches the model.
  • Low confidence → forced to HYBRID, regardless of what the model's top guess was. This is the safety net: "not sure" always means "search both backends," never "guess and skip one."

The threshold (currently 0.8) isn't a guess — it's computed at training time by a sweep: try every cutoff from 0.1 to 0.9, and for each one measure accuracy only on the predictions that clear that cutoff. The winning threshold is the highest one that doesn't drag accuracy below the model's overall accuracy. Higher threshold = more queries get pushed to safe HYBRID; lower threshold = more queries get to use the faster single-engine route. It's a dial, not a constant.

The same label does double duty beyond just "which backend": it also picks the ES field-boost profile (es_client.py::_BOOST_PROFILES) and the RRF fusion weights per source (rerank.py::_LABEL_RRF_WEIGHTS). One classification, three downstream effects.

Hard rule — don't touch RRF fusion weight stays neutral (1.0/1.0) regardless of category anywhere else in the system — category-based weighting was proposed and explicitly rejected during design. See CLAUDE.md rule 4.

Where each hop lives:

  1. packages/retrieval-api/.../ws.py — WebSocket handler, reads auto_route from the client message (gated by a settings flag).
  2. instant/search.py::run_instant — the orchestrator. Corrects the query, calls the classifier, builds the routing plan, fires ES/Milvus tasks concurrently, fuses.
  3. common/es_client.py / common/milvus_client.py — the actual backend calls, only invoked if the plan says so.
  4. instant/rerank.py::rerank_instant_results — fuses (or passes through) results per the plan.
  5. web/src/components/TracePanel.tsx — renders the classifier trace step in the UI: which label, what confidence, and (if auto-route is on) exactly which backends got hit.

08 Training it further

You will retrain this when: the classifier gets a real query wrong in production, you're adding coverage for a new query pattern, or you've expanded the legal lexicon and want the gazetteer features to benefit.

Step 1 — Add examples

Edit packages/common/data/instant_classifier/train.jsonl. One JSON object per line:

{"query_text": "Section 80C deduction limit", "label": "KEYWORD"}
{"query_text": "can I claim HRA if I live with my parents", "label": "INTENT"}

Never touch eval_frozen.jsonl — it's the frozen 24-example yardstick used to score every retrain. If you add examples there, you lose the ability to compare accuracy across model versions.

Step 2 — Retrain

uv run python packages/common/scripts/train_instant_classifier.py

This fits a fresh pipeline on train.jsonl, scores it against eval_frozen.jsonl, sweeps the confidence threshold, and overwrites instant_classifier_model.joblib + instant_classifier_model_meta.json. It prints the new meta JSON — check overall_eval_accuracy and confidence_threshold before committing.

Step 3 — Verify

uv run pytest packages/common/tests/test_instant_classifier_eval.py -v

This is a CI guard: it loads the committed artifact and asserts eval accuracy stays ≥ 0.7. If your retrain drops below that, something in your new examples is probably mislabeled or contradictory to existing ones — don't just lower the floor to make it pass.

Step 4 — Commit

Commit the .joblib and _meta.json together with your train.jsonl change. There's no CI auto-retrain — this is a manual, reviewed step by design.

Adding a 4th label? Don't. The routing table (labels.py::_ROUTING) is a fixed 3-way switch tied directly to "which of our two backends to hit." A new label needs a new routing decision to go with it — that's a design change, not a training-data change. Talk to whoever owns docs/superpowers/specs/2026-08-20-instant-mode-query-classifier-design.md first.

10 Gotchas & FAQ

Model missing on startup?
App crashes on purpose (FileNotFoundError) — fail-loud by design, not a bug to silently work around.
Confidence looks oddly high always?
3-class softmax can't go below ~1/3 — a threshold under 0.33 never gates anything, that's expected.
Where do I see it working live?
Open the TracePanel in the web UI for any Instant Mode query with tracing on — look for the "Classifier" step.
auto_route is off, does the classifier still run?
Yes — it still classifies and the label still drives ES boost profile and shows in the trace, it just doesn't skip any backend.
Can I swap in embeddings for better accuracy?
That defeats the point — sub-5ms CPU-only is a stated design goal. Bigger accuracy gains should come from better training examples, not a heavier model.
